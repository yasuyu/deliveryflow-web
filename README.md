# DeliveryFlow Web

DeliveryFlowは、配達員の「勤務開始 → オファー確認 → 受諾 → 荷物受取 → 配達完了」をブラウザで試せる学習用Webアプリです。

このリポジトリは、企業ハッカソンで得た学びをもとに、個人学習用として設計・実装したポートフォリオです。実在企業から提供されたコード、資料、内部仕様、秘密情報は含みません。

基本機能は自分のPC内で無料で動かせます。任意のAI振り返り機能はOpenAI APIの従量課金を利用します。普段の開発にはSQLite、本番に近い確認にはDocker ComposeとPostgreSQLを使います。

## 設計上の特徴

完成画面では、京都中心部の実地図を全面に表示し、その上にスマートフォン向けの4段階ボトムシートを重ねています。配達員は登録、勤務開始、オファー確認、受諾、荷物受取、配達完了、退勤サマリーまでを1つの画面で試せます。

主な特徴は次の3点です。

- **状態遷移と再送の安全性**: 先着1人だけが受諾できるオファー、`Idempotency-Key`による二重受諾・二重完了・二重加点の防止、通信切断中の操作キューを実装しています。
- **スマートフォン実機を意識したUI**: OpenStreetMapの地図、最小化できるボトムシート、固定された主要操作、ホーム画面追加用のPWA設定により、配達中の片手操作を想定しています。
- **ローカルで検証しやすい品質管理**: SQLiteで素早く開発し、Docker ComposeとPostgreSQLで本番に近い確認を行い、OpenAPI、テスト、GitHub Actions CIで振る舞いを確認します。

主な技術は、Node.js、Prisma、SQLite、PostgreSQL、Docker Compose、WebSocket、Leaflet/OpenStreetMap、PWA Manifest、OpenAPI、Node.js標準テストランナーです。

## できること

- 配達員の登録、6桁PINでのログイン、ログアウト
- 正しい状態遷移に沿った配達操作
- 退勤時の稼働時間、完了した配達件数、獲得ポイントの勤務サマリー
- APIキー不要・外部通信なしで退勤時に表示する、約200文字の無料の定型振り返り
- 勤務終了後にボタンで生成する、約200文字のAI振り返り（OpenAI APIの設定が必要）
- 配達履歴の検索と絞り込み、「さらに読み込む」による過去の実績・加点内訳の20件ずつの追加表示
- 基本点、配達距離・雨天・深夜ボーナス、称号、月間・14日間・全期間ランキング
- 初期状態の京都デモ位置、明示的に許可した端末位置、外部通信しない模式図、同意後にGoogle Mapsで開く道路経路とナビ
- 現在地→店舗→配達先の道路沿いの標高グラフと、その横の最高・最低標高（京都中心部、スコア加算なし）
- 店舗に近い順で最大N人へ同時に送るオファーと、先着1人の受諾確定
- 認証済みWebSocketによる状態変更の即時反映と、自動再接続・定期更新へのフォールバック
- 通信切断中の受諾・荷物受取・配達完了を端末へ保存し、接続復旧後に同じ冪等キーで順番に再送
- SQLiteとPostgreSQLの両方で同じAPIを実行
- OpenAPI仕様、テスト、CIによる動作確認
- 京都市内の複数の仮想店舗・配達先から、重複を避けて選ぶデモオファー
- ランキングと称号をすぐ確認できる、事前登録済みのデモ配達員と配達実績

## まず動かす

必要なものはNode.js 22以上とnpmです。PowerShellでリポジトリを開き、次を実行します。

```powershell
Copy-Item .env.example .env
npm ci
npm run db:migrate
npm run db:generate
npm start
```

起動後に開く場所:

- アプリ: <http://localhost:3000>
- API仕様: <http://localhost:3000/docs>
- ヘルスチェック: <http://localhost:3000/healthz>

ログイン後は、地図を広く見せる縮小状態から始まります。地図は画面全体へ表示し、その上にボトムシートを重ねるため、シートの左右や角の外側にも地図が続きます。上部に配達状況と14日間・累計スコア、下部に受取場所・配達先・座標・報酬と緑の主要操作ボタンを表示します。スマートフォンでの配達操作を想定し、カードはアイボリーの背景と緑のアイコンで統一しています。

上部の勤務状態・スコア・メニューは地図より前に固定表示し、スマートフォンのキーボードや拡大表示で表示領域が上下にずれた場合も、その上端へ位置を合わせます。

シートはハンドルのドラッグ、タップ、上下キーで最小化・縮小・中間・拡大の4段階にできます。最小化するとハンドルだけを画面下部に残して地図を広く確認できます。詳細は広げたシートで確認でき、実績は上部スコア、設定は右上のメニューボタンからも開けます。

通常のシートには配達情報と主要操作だけを表示します。実績は上部のスコア、設定は右上のメニューから開き、各画面の「配達画面へ戻る」で復帰します。受諾・受取・完了などの主要操作は、詳細をスクロールしても下部に残ります。縮小時は店舗・届け先・報酬も表示し、シートを広げると同じ情報の重複を隠して詳細欄を広く使えます。

オファーの受付時間は画面に表示してから30秒です。期限が切れると、オンラインでは次のオファーを自動表示します。オフライン、候補なし、通信エラーの場合は自動処理を止め、「最新の状況を確認する」操作または理由を表示します。

「辞退する」は勤務を続けたまま辞退します。「辞退して退勤」は確認後に勤務を終了し、キャンセルした場合はオファー・勤務状態を変更しません。

自動更新では同じ配達の詳細の開閉とフォーカスを保持します。シートは上下キー・Home・Endで操作できます。現在地・地図・天候・ログアウトは右上の「設定」、スコア・ランキング・履歴は上部のスコアから開きます。ランキングは「今月」「14日間」「全期間」をタブで切り替え、順位・配達員名・称号・ポイントを1列で読みやすく表示します。

### スマートフォンのホーム画面へ追加

HTTPSのURLで開くと、DeliveryFlowを専用アイコン付きのWebアプリとしてホーム画面へ追加できます。iPhoneはSafariの共有メニューから「ホーム画面に追加」を選び、「ウェブアプリとして開く」を有効にします。AndroidはChromeのメニューから「アプリをインストール」または「ホーム画面に追加」を選びます。ホーム画面から起動すると、対応ブラウザーではアドレスバーのない独立した画面で表示されます。

ホーム画面へ追加してもサーバーへの接続は必要です。公開URLを変更すると以前のアイコンから開けなくなるため、継続利用には固定HTTPS URLを使用してください。

## 京都の実地図

ログインすると、OpenStreetMapの地図を自動で読み込みます。Leafletはnpmで固定バージョンを導入し、アプリと同じサーバーから配信します。地図表示にAPIキーや有料契約は不要です。

- 初期表示は京都市中心部（三条・鴨川周辺）。配達中は注文の受取場所と配達先を表示します。
- オファー確認中は現在地から店舗と店舗から配達先の両方を表示します。受諾後から受取前は現在地から店舗だけを灰色の点線で結び、受取後は店舗から配達先だけを青い点線で結びます。配達中は進行中ではない区間の線と地点を地図から隠します。いずれも直線で、道路に沿った経路計算や所要時間の算出は含みません。
- 地図を有効にすると、表示エリアのタイル情報とIPアドレスがOpenStreetMapへ伝わります。端末位置へ切り替えた場合は、約100m単位に丸めた現在地を含む周辺の地図タイルを読み込みます。
- ログイン中は自動で地図を表示します。「設定」で通信を停止・再開でき、ログアウト時にも停止します。通信できない場合も配達操作は使えます。
- 地図の出典を常に表示し、ブラウザのキャッシュを利用します。一括保存やオフライン用の事前取得は行いません。
- 無料の地図配信には稼働保証がありません。公開・利用拡大時は[OpenStreetMapの利用条件](https://operations.osmfoundation.org/policies/tiles/)を確認し、配信先を再検討します。

## 画面で試す順番

1. 認証画面で「新規登録」を選び、名前と6桁PINを入力して配達員を登録します。
2. 「稼働を開始する」を押します。
3. 初期状態の京都デモ位置を使うか、必要な場合だけ「設定」の「実際の現在地を使う」を押してブラウザの位置情報を許可します。
4. 「オファーを確認する」を押します。
5. 配達詳細で、見込みスコア、直線距離、標高グラフ、経路プレビューを確認します。
6. 受諾、荷物受取、配達完了の順に進めます。
7. 業務が終わったら退勤します。今回の稼働時間・完了件数・獲得ポイントが表示され、保存中の現在地はこの時点で削除されます。

退勤直後はボトムシートを拡大し、勤務サマリーと「AIで振り返る」が見える位置へ移動します。

雨天ボーナスは「設定」の「天候シミュレーター」で確認できます。外部の気象APIには接続しません。

標高は同梱したOpenStreetMapの道路データと国土地理院の標高データからローカル計算します。現在地→店舗→配達先を表示し、荷物受取後は店舗→配達先へ切り替えます。グラフの横に最高・最低標高、横軸に地点名と出発地点からの道路沿いの距離を表示します。距離の基準を区別するため、グラフの横軸には「道路沿いの距離（参考）」、経路プレビューの見出しと各区間には「直線距離」「直線」を明記します。道路沿いの距離と直線距離は同じ値とは限りません。京都中心部の対象外やデータ不足では取得不可を表示し、橋・トンネルの路面標高や通行規制は扱いません。地図の点線表示・直線距離によるスコアは従来どおりです。データの出典・対象範囲・再生成方法は[標高データの説明](apps/server/assets/README.md)に記載しています。

## 勤務終了後のAI振り返り

退勤すると、勤務サマリー内の「無料の振り返り」に約200文字の定型コメントを自動表示します。サーバーで確定した勤務時間・配達件数・獲得ポイントに触れ、0件の勤務や長い勤務に合わせて案内を変えます。APIキー・外部通信・追加料金は不要です。AI生成の文章とは区別して表示し、AIが未設定・生成失敗の場合も読めます。

退勤サマリーの「AIで振り返る」を押すと、サーバーで確定した勤務時間・配達件数・獲得ポイントをもとに、日本語約200文字のフィードバックを表示します。ボタンを押したときだけ外部APIを呼びます。氏名、PIN、現在地、店舗・配達先の情報はOpenAIへ送りません。

SQLite版は`.env`、普段使うPostgreSQL版は`.env.postgres`に次の設定を追加してください。キーは自分の環境のファイルへ入力し、Gitやチャットへ貼り付けないでください。

```dotenv
OPENAI_API_KEY=your-api-key
OPENAI_MODEL=gpt-4.1-mini
```

設定後、SQLite版は`npm start`で再起動します。PostgreSQL版は監視中のターミナルをCtrl+Cで止めてから、同じ作業フォルダーで`npm run dev:postgres`を実行し、アプリの環境変数を反映してください。`.env.example`と`.env.postgres.example`ではキーを空にしてあり、未設定時は外部通信しません。

APIキーはサーバーの環境変数からだけ取得し、ブラウザーへ配信するファイル・APIレスポンス・ログには含めません。[OpenAI Responses API](https://developers.openai.com/api/docs/guides/text)をサーバーから呼び出し、`store: false`、出力上限600トークン、15秒のタイムアウトを設定しています。生成内容は180〜220文字を指示し、表示は最大240文字に制限します。AIの文章は参考として確認してください。

OpenAI APIの利用には[APIの従量料金](https://developers.openai.com/api/docs/pricing)が別途かかります。同じ勤務の生成は最大1回で、連打・通信切断後の再送・サーバー再起動後はDBに保存した結果を返します。生成失敗時も勤務実績とポイントは記録済みで、退勤を取り消しません。重複課金を避けるため、同じ勤務で失敗後の再生成は行いません。サーバー停止で生成が中断された場合、30秒以降の結果取得で生成失敗を表示します。勤務サマリーの画面表示は従来どおり退勤直後から次の勤務開始・ログアウト・ページ再読み込みまでです。

自動テストはOpenAIの応答をモックし、実際のAPI料金を発生させずに検証します。DB構造とSQLite/PostgreSQLのMigrationは変更しません。

## ポートフォリオ用デモデータ

このアプリは、店舗側の管理画面を持たず、配達員がオファーを受けて配達を完了する体験に絞っています。起動時に、既存データを変更せず、次の学習用データが不足している場合だけ自動で追加されます。

- 京都市中心部のデモ店舗5件
- 京都市内のデモ配達先10件と、地点ごとに異なる配達報酬
- ランキング表示専用のデモ配達員5人
- 基本点・雨天・深夜ボーナスで作った過去の配達実績

新しいオファーは店舗と配達先の50通りから選びます。直近6件と同じ組み合わせを候補から外すため、短いデモ中に同じ経路が続きにくくなっています。

デモ配達員はランキングと称号の説明専用で、PINを持たずログインできません。自分のデモ用配達員は画面から登録してください。新規登録直後はランキング下位から始まり、配達完了による順位・スコア・称号進捗の変化を確認できます。

デモデータの追加処理は繰り返し実行しても重複しません。既存の配達員、注文、履歴、店舗は削除・初期化しません。

SQLite版のランキング用デモ実績だけを初期状態に戻す場合は、次を実行します。

```powershell
npm run demo:reset
```

PostgreSQL版では、Composeを起動した状態で次を実行します。

```powershell
docker compose --env-file .env.postgres exec app node scripts/demo-data.js --confirm-demo-reset
```

どちらのコマンドも、ランキング表示専用の5人に紐づく`ランキング実績`だけを作り直します。画面から登録した配達員、その注文・履歴・スコア、既存店舗は変更しません。

## 設定ファイル

`.env`はPCごとのローカル設定です。Gitには保存されません。

```env
DATABASE_URL="file:./delivery.db"
PORT=3000
OFFER_TTL_SECONDS=30
OFFER_CANDIDATE_LIMIT=3
# SCORE_BONUS_SIMULATED_NOW="2026-09-14T22:00:00+09:00"
```

- `DATABASE_URL`: SQLiteファイルの場所。Prisma Schemaからの相対位置です。
- `PORT`: アプリのポート番号。
- `OFFER_TTL_SECONDS`: オファーが期限切れになるまでの秒数。標準は30秒です。
- `OFFER_CANDIDATE_LIMIT`: 1注文あたり同時にオファーを送る近い順の人数（初期値3）。
- `SCORE_BONUS_SIMULATED_NOW`: 深夜ボーナスを日中に試す場合だけ指定します。

PostgreSQL版の受付時間を変える場合は、起動に使う`.env.postgres`を更新し、Compose Watchをいったん終了してから起動し直します。稼働中のコンテナには古い環境変数が残るため、単なる再起動ではなくアプリの再作成が必要です。複数の作業フォルダーを使う場合は起動元を統一し、`COMPOSE_PROJECT_NAME`を既存環境に合わせてDBの保存先を保ちます。

## 現在地とプライバシー

勤務開始時は京都市役所付近のデモ位置を使います。端末位置は「実際の現在地を使う」を押したときだけブラウザへ要求し、自動追跡やバックグラウンド取得は行いません。

- 保存できるのは勤務中だけです。
- 端末位置はブラウザ内で小数第3位へ丸めてから送信し、サーバーでも同じ精度へ正規化します。京都市内ではおおむね100m単位です。
- 勤務中に保存した最新位置は、最終更新から12時間だけ候補選定と距離計算に使います。
- 店舗から近い順に最大`OFFER_CANDIDATE_LIMIT`人を候補にし、最初に受諾した1人へ確定します。残りのオファーは取り下げます。
- 退勤時、または最終更新から12時間経過後の定期処理で、緯度・経度・精度・位置種別・更新時刻をDBから削除します。
- API画面には配達員本人の正確な緯度・経度を返しません。
- 距離は外部地図へ送らず、サーバー内で直線距離として計算します。
- 配達詳細の経路プレビューも外部通信せず、地点の順番と直線距離だけを模式図として表示します。
- 配達詳細には、テスト注文の配達報酬、店舗・届け先の学習用座標、現在の進行案内も表示します。
- オファー確認中は「Google Mapsで道路経路を確認」、受諾後は「店舗までの経路をGoogle Mapsで開く」、受取後は「配達先までの経路をGoogle Mapsで開く」を表示します。
- 確認画面で同意した場合だけ、店舗・配達先のデモ座標をGoogle Mapsへ送ります。デモ位置の利用中は京都市役所付近を出発点として送り、端末位置の利用中はDeliveryFlowから現在地を送信せずGoogle Maps側の現在地を使います。受取後は店舗を出発点にします。
- ブラウザーで取得した元の高精度な座標はLocalStorageへ保存せず、丸めた座標だけを画面メモリーと勤務中のDBに保持します。
- 新しく作る店舗と届け先は京都市中心部の学習用仮データです。以前のBKC周辺の店舗・注文・配達履歴は変更しません。

公開環境では、ブラウザーからサーバーまでの通信を保護するためHTTPSを必須にしてください。

配達詳細内の経路プレビューは模式図で、背景の実地図上の点線も直線です。道路に沿った距離と所要時間、配達中のナビは、同意後に開くGoogle Maps側で確認します。端末や位置情報の状態によっては、ナビではなく経路プレビューが開きます。Google Mapsは外部サービスのため、インターネット接続と同サービスの提供状況に依存します。

## リアルタイム更新

ログイン後は同一サーバーの`/api/realtime`へWebSocketで接続し、注文や勤務状態が変わった通知を受けると、認証済みAPIから最新状態を再取得します。イベントには注文内容や位置情報を含めません。

- アクセストークンはURLへ付けず、WebSocketサブプロトコルで接続時だけ送ります。
- 切断時は間隔を広げながら自動再接続し、その間は10秒ごとの更新へ戻ります。
- 接続中も取りこぼし対策として60秒ごとに状態を確認します。
- 画面ロック・別アプリ・ブラウザーの履歴から戻った際は接続を作り直し、配達状態をすぐ確認します。復帰時も選択中の設定・実績ビューとシートの段階を保持します。
- 現在の配信先は同じNode.jsプロセスへ接続中の画面です。複数サーバー間の配信は将来Redisなどが必要です。

## オフライン操作キュー

画面を開いたまま通信が切れた場合、オファー受諾・荷物受取・配達完了はブラウザーの端末内へ保存されます。接続が戻ると、保存した順に自動送信します。

- 最初の送信で使った`Idempotency-Key`を再送でも維持します。状態変更と再送応答を同じDBトランザクションで保存するため、処理途中の停止でも片方だけが残らず、応答を受け取れなかった場合も二重受諾・二重完了・二重加点を防げます。
- キューは配達員IDごとに分け、アクセストークン、PIN、現在地は保存しません。
- オファー確認、辞退、勤務開始・終了、現在地更新、天候変更は保存対象外です。通信が必要な操作として、その場でエラーを表示します。
- 期限切れや他端末での状態変更により競合した操作は自動で削除しません。画面から同じキーで再送するか、送信待ちを取り消して最新状態へ戻せます。
- 旧版で応答が未保存の受諾・受取・完了は、本人の配達記録を確認して復旧します。実行済みの場合は現在の状況と保存済みの加点結果を返し、重複処理しません。勤務操作など結果を確定できない旧記録は、最新状態を確認して新しい操作として実行します。
- ページ自体のオフライン起動や地図タイルの保存は対象外です。すでに開いている配達画面で一時的な切断を補います。

## スコアの仕組み

配達完了の基本点は100ポイントです。店舗から配達先までの直線距離が500mを超えると、超過分250mごとに10ポイント、最大100ポイントの距離ボーナスを追加します。さらに雨天は30ポイント、日本時間22:00以上または5:00未満は50ポイントを追加します。

見込みスコアはオファー作成時に固定されます。その後に天候や時刻が変わっても、受諾済みの配達で獲得するポイントは変わりません。同じ完了操作を再送しても二重加点されません。

## PostgreSQL版を動かす

Docker Desktopを起動し、設定ファイルを作成します。

```powershell
Copy-Item .env.postgres.example .env.postgres
docker compose --env-file .env.postgres up --build -d --wait
```

ブラウザで <http://localhost:3106> を開きます。停止は次のコマンドです。

```powershell
docker compose --env-file .env.postgres down
```

`down`だけならDBボリュームは残ります。`down -v`はDBデータも削除するため、明確に初期化したい場合以外は実行しないでください。

PostgreSQL版も同じホーム画面追加機能を利用できます。固定HTTPS URLの転送先をPostgreSQL版のポート（標準は3106）へ設定してください。URLを維持すれば、既存のホーム画面アイコンをそのまま利用できます。SQLiteとPostgreSQLの配達員・履歴・スコアは別々に保存されるため、切替後はPostgreSQL側の配達員でログインするか、新規登録します。DBの切替だけでは既存データは移行されません。

SQLiteだけをDockerで動かす場合は、ルートをビルドコンテキストに指定します。

```powershell
docker build -f apps/server/Dockerfile -t deliveryflow-web .
docker run --rm -p 3000:3000 -v deliveryflow-data:/data deliveryflow-web
```

### PostgreSQL版の開発を再開する

VS Codeでは最新コードを同期したリポジトリのフォルダーを開き、そのフォルダーのターミナルから実行します。

```powershell
npm run dev:postgres
```

起動時にイメージをビルドし、その後のコード変更をCompose Watchで反映します。別の作業フォルダーから同じComposeプロジェクトを起動すると、そのフォルダーのコードで既存アプリが再作成されます。古いフォルダーの監視は`Ctrl+C`で終了し、起動元を統一してください。

監視を停止した状態で、DBを残してアプリだけを最新コードへ戻す場合は、最新リポジトリのターミナルで次を実行します。`Ctrl+C`でDBも停止していた場合は、先に既存DBを`start db`で起動します。

```powershell
docker compose --env-file .env.postgres start db
docker compose --env-file .env.postgres up --build --no-deps --force-recreate -d --wait app
```

このコマンドは起動中のDBコンテナとボリュームを再作成しません。既存環境と同じ`COMPOSE_PROJECT_NAME`を使います。

### バックアップと復元

DB起動中に`npm run backup:postgres`で、Git管理外の`data/backups/`へバックアップとチェックサムを保存できます。`npm run restore:postgres -- --file ...`は新しい復元用DBだけに復元し、普段使うDBや既存DBは上書きしません。`npm run test:backup:postgres`で全データとID採番の一致、既存DBへの上書き拒否を確認できます。

実行例、復元したDBへの接続先変更、スマートフォンの画面ロック・通信切断後の確認方法は[ローカル運用の手順](docs/local-operations.md)を参照してください。

## テストとCI

```powershell
npm run check
npm test
```

テストは開発用DBを変更せず、毎回一時SQLite DBを作成します。配達状態、認証、冪等性、履歴、スコア、ランキング、位置情報、WebSocket認証と順序付き通知、オフライン操作の順序と競合停止を確認します。

ブラウザーE2Eは、初回にChromiumとWebKitを導入してから実行します。

```powershell
npx playwright install chromium webkit
npm run test:e2e
```

デスクトップとスマートフォン幅で、登録から配達完了、加点・履歴の保存、退勤サマリーまで確認します。専用の一時SQLite DBと空きポートのサーバーを自動作成し、終了時に片付けます。外部地図タイルはテスト用画像へ置き換えます。失敗時のスクリーンショットとトレースはGit管理外の`test-results/`へ保存します。

上部カードの表示はiPhone相当のWebKitでも検証します。初回ログイン・再読み込み・短い画面に加え、Visual Viewportの上下のずれを模擬し、勤務状態・スコア・メニューが隠れず操作できることを確認します。実際のiOSキーボードやホーム画面からの起動は、スマートフォン実機で確認します。

Pull RequestではGitHub Actionsが次を自動確認します。

- Node.js 24での依存関係再現
- SQLite Migration、構文チェック、全テスト
- Chromiumでのデスクトップ・スマートフォン幅のE2Eテストと、WebKitでの上部カード表示・中断からの復帰テスト
- PostgreSQLコンテナのビルド、Migration、APIスモークテスト、バックアップと別DBへの復元検証

## 困ったとき

### 直線距離が表示されない

1. 最新の`main`をpullします。
2. `npm run db:migrate`と`npm run db:generate`を実行します。
3. アプリを再起動し、ブラウザを再読み込みします。
4. 勤務開始後はデモ位置が自動設定されます。端末位置を試す場合だけ「実際の現在地を使う」を押します。
5. オファーを確認し、「配達詳細」の「現在地 → 店舗」を見ます。

「店舗 → 届け先」は現在地がなくても表示されます。Docker版はコード変更後に`--build`を付けて再作成してください。

### DB構造を変更した

SQLiteとPostgreSQLのSchema・Migrationを両方更新し、両方のPrisma Clientを検証します。DBファイルや生成済みClientはGitへコミットしません。
