# 性能確認

この文書は、現在利用できる簡易負荷試験とメトリクスの確認方法を説明します。現段階では1台のPCで使う学習用アプリを対象とし、外部公開サービスの性能保証は行いません。

## 現在測定できる範囲

`scripts/load.js`は、起動中のアプリの`GET /healthz`へ複数リクエストを送り、次を集計します。

- 成功数と失敗数
- 全体の所要時間
- 1秒あたりの処理件数
- 平均応答時間
- 最大応答時間
- 最大5件の失敗内容

対象URLは安全のため`localhost`、`127.0.0.1`、`::1`だけを許可します。配達の登録・受諾・完了など、DBを更新するAPIへの負荷試験ではありません。

## 基本の実行方法

1つ目のPowerShellでアプリを起動します。

```powershell
npm start
```

2つ目のPowerShellで負荷試験を実行します。

```powershell
npm run load-test
```

初期値は100件、同時10件です。PostgreSQL版を対象にする場合はURLを変更します。

```powershell
$env:LOAD_TEST_URL = "http://127.0.0.1:3106/healthz"
npm run load-test
```

## 件数と同時数を変更する

```powershell
$env:LOAD_TEST_REQUESTS = "500"
$env:LOAD_TEST_CONCURRENCY = "20"
npm run load-test
```

| 環境変数 | 初期値 | 意味 |
|---|---:|---|
| `LOAD_TEST_URL` | `http://127.0.0.1:3000/healthz` | 確認するローカルURL |
| `LOAD_TEST_REQUESTS` | `100` | 合計リクエスト数 |
| `LOAD_TEST_CONCURRENCY` | `10` | 同時に動かす処理数 |

値は正の整数で指定します。同時数を急に大きくせず、10、20、50のように段階的に上げます。

## 結果の読み方

```json
{
  "requests": 100,
  "concurrency": 10,
  "successful": 100,
  "failed": 0,
  "requestsPerSecond": 250,
  "averageResponseMilliseconds": 20,
  "maximumResponseMilliseconds": 80
}
```

最初に`failed`が0であることを確認します。次に、同じPC・同じDB・同じ設定で以前の結果と比較します。PCの性能や起動中のソフトによって数値が変わるため、異なる環境の値を単純比較しません。

固定の合格値を先に決めるより、通常状態を基準値として記録し、変更後に平均・最大応答時間が大きく悪化していないかを確認します。失敗が発生した場合は、応答時間より先に原因を調べます。

## アプリのメトリクス

起動後に <http://localhost:3000/metrics> を開くと、プロセス起動後の次の値を確認できます。

- リクエスト総数
- 5xxサーバーエラー数
- 平均応答時間
- プロセス稼働時間

PostgreSQL版は <http://localhost:3106/metrics> です。配達員の名前、PIN、トークン、正確な座標などは含みません。

負荷試験の前後でメトリクスを比較すると、送信件数が反映されたかを確認できます。メトリクスはプロセスを再起動するとリセットされます。

## 測定時の条件

結果を残す場合は、次の条件も一緒に記録します。

| 項目 | 記録例 |
|---|---|
| 日時 | 2026-09-15 14:00 JST |
| DB | SQLite / PostgreSQL |
| URL | `/healthz` |
| 合計件数 | 500 |
| 同時数 | 20 |
| 成功・失敗 | 500 / 0 |
| 平均・最大 | 20ms / 80ms |
| 変更内容 | スコア集計処理を変更 |

測定中は、可能であれば大きなダウンロードや別の負荷試験を止め、同じ条件をそろえます。

## ボトルネックを調べる順番

1. `failed`の内容とHTTP状態コードを確認します。
2. `/metrics`で5xxエラーと平均応答時間を確認します。
3. サーバーの構造化ログで遅いリクエストとエラーを確認します。
4. SQLite版とPostgreSQL版を同じ件数・同時数で比較します。
5. DBを使う処理で遅い場合は、対象クエリ、絞り込み条件、インデックスを確認します。
6. 再現条件を自動テストまたは専用スクリプトとして残します。

SQLiteは軽量な開発・テスト向けで、書き込みを多く並行させる用途には制約があります。本番に近い同時接続の確認はPostgreSQL版で行います。

## 現在の制限

- 負荷試験の対象は`/healthz`だけです。
- パーセンタイル値（p50、p95、p99）は集計しません。
- 長時間試験、ネットワーク遅延、複数PCからの同時接続は扱いません。
- DB更新を伴う配達APIのシナリオ負荷試験はありません。
- GitHub Actionsでは通常のテストとPostgreSQLスモークテストを実行し、負荷試験は実行しません。

配達APIの性能を測る場合は、開発用データを変更しない独立DB、配達員ごとの認証、操作ごとの`Idempotency-Key`、状態遷移を考慮した専用シナリオが必要です。単純に完了APIを繰り返し呼ばないでください。

## 次に拡張するとき

性能上の必要性が確認できた段階で、次を検討します。

1. p50・p95・p99の集計
2. 読み取りAPIと書き込みAPIを分けたシナリオ
3. PostgreSQLのクエリ計測とインデックス確認
4. WebSocket追加時の接続数・再接続試験
5. 複数サーバー化が必要になった場合のRedisと共有状態

測定結果を根拠に追加し、将来構成のためだけに複雑な基盤を先に導入しません。
